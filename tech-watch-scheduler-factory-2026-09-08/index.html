Tech Watch Scheduler Factory — Self-watch baseline

A real end-to-end self-test validates the two-prompt flow, separate public Pages repository, capability checks, and lease/retry runtime. The main friction observed was repository access when the website repo was created manually.

Baseline conclusion

The factory has now been run against itself through its own PREPARE and ACTIVATE contracts. The result supports the current architecture: two short user prompts, a repository-specific watch contract, separate watch and post-mortem cadence, a public website projection, and bounded runtime recovery.

Operational lesson: when permissions allow it, prefer letting the connected GitHub App create the *-website repository. In this self-test, a manually created website repository initially returned 403 Resource not accessible by integration until repository access was explicitly granted.

1. ChatGPT Scheduled Tasks

Current OpenAI documentation supports recurring and monitoring tasks, while availability and connected-app capabilities remain dependent on the account and execution context. External actions can require approval. The factory therefore keeps capability checks and verified-state reporting as first-class requirements.

OpenAI — Scheduled tasks in ChatGPT

2. GitHub access and Pages

GitHub Apps can be installed for selected repositories, which means repository visibility to the App is distinct from the App's endpoint permissions. This self-test reproduced that boundary directly. GitHub Pages continues to support branch publication from /(root) or /docs, matching the factory's separate static website contract.

GitHub — Review and modify installed GitHub Apps
GitHub — Configure a Pages publishing source

3. Runtime reliability

The multiplexed runtime uses deterministic dispatch identity, a bounded lease, bounded retry, and a failed archive. These choices align with established queue reliability patterns: work becomes recoverable after a visibility timeout, and retried work must be designed for idempotence because duplicate delivery remains possible.

4. User-facing flow

The public entry point remains intentionally small: one short prompt reads prompts/PREPARE.md, and a second reads prompts/ACTIVATE.md. The detailed authority stays versioned in Git rather than being copied into a long README prompt.

After each validated T0 or UPDATE, the watch creates or updates the separate public website repository, adds the dated edition, and refreshes the home and archive.

Initial cadence

  • Watch: every 7 days.
  • Post-mortem: every 30 days, after enough runs exist to judge noise and useful signal.
  • New issues from this baseline: none. The observed findings are already represented by current contracts.

Limits

This baseline validates the public product flow and the primary external dependencies needed by that flow. It does not claim exhaustive coverage of distributed scheduler research or of every user's experience.
