Tech Watch Scheduler Factory — Recovery, event signals and same-occurrence resume

UPDATE 001 is now complete: the self-hosting inventory fix remains valid, the factory has a dedicated same-occurrence recovery path, and OpenAI's event-triggered tasks are worth evaluating as an optional GitHub signal rather than a replacement for periodic research.

What changed

The first UPDATE occurrence had a real finding but was never closed with its full research receipt and website delivery. Recovery resumed that same occurrence rather than starting a new weekly cycle.

Recovery result: the watch is complete. The public files are delivered, while GitHub Pages activation remains a separate unverified setting and is not presented as live.

1. Self-hosting defect remains fixed

The factory's strict package inventory validator originally treated the generated scheduler-techno/ runtime directory as distributable source. Commit 14e45a6 fixed that by excluding generated watch state without changing the distribution manifest.

2. Recovery is now a first-class runtime path

The current dedicated runtime adds a six-hour technical recovery task. It acts only on the latest incomplete occurrence, resumes that exact occurrence from durable state, and requires positive current evidence before treating another writer as concurrent. This recovery exercised those semantics directly.

That design is consistent with established failure models: visibility timeouts can make work redeliverable, durable execution should resume persisted progress after failure, and retries should be bounded.

3. OpenAI now documents event-triggered Scheduled Tasks

OpenAI's current Scheduled Tasks documentation and its 25 August 2026 release notes describe tasks triggered by supported app events, including Gmail, Slack and GitHub pull-request activity. For this factory, that is an optional signal path—not a substitute for the weekly watch, which still needs open-web and multi-source research.

A follow-up proposal was opened as issue #7: evaluate periodic | periodic+event with stable deduplication, no extra authority from the event, and periodic fallback.

4. GitHub repository delivery and Pages remain separate

The public website repository is separate from the canonical source repo and accepts writes through the connected GitHub integration. GitHub's documentation continues to distinguish repository selection from API permissions, and Pages can publish from main at the repository root.

This run can verify committed website files, but the available integration does not expose a Pages-settings mutation/status operation. A live Pages URL is therefore not claimed.

Decision

  • Keep: weekly periodic watch as the authoritative research cycle.
  • Keep: six-hour recovery only for the latest incomplete occurrence.
  • Evaluate: event-triggered GitHub activity as an optional low-latency signal.
  • Keep separate: website file publication and actual Pages activation.

Limits

Event-triggered support is product- and connection-dependent and the documented GitHub event surface is narrower than this watch. Queue and durable-execution products are used as transferable failure models, not as claims that ChatGPT implements the same infrastructure.
